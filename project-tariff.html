Background

This was group coursework, in a group of three. The course brief described an electricity retailer that wanted customers to upload their usage and compare what they would pay under flat, time-of-use and tiered tariffs. The task was a working prototype with tests, plus the project management documents and a report.

The project management work and the report were the team’s: a project charter, a work breakdown structure, a schedule, a risk register, quality metrics, use cases and interface wireframes, written up in one report. I wrote the pricing logic (the three tariff models), the tests, the command-line interface and the Flask web interface, and I designed the web page. That is the part I am claiming. The rest is the team’s.

The report centres on the command-line build: one Python file with four functions and a short prompt loop. It treats a web interface only as wireframes for a later phase. The Flask web interface I wrote is a separate build with its own, larger calculation module, and the test and coverage figures on this page do not describe it.

Pricing

Each tariff model is a function that takes plain inputs, the hourly usage and the tariff’s rates, and returns a small result. Reading the file is a separate function, so the pricing functions never touch files, and any interface can call them without changes.

  • Flat rate multiplies the total kWh by one rate and adds a fixed fee.
  • Time-of-use puts each reading into peak, off-peak or shoulder by its hour of the day. A window can wrap past midnight, so an off-peak window of 22 to 7 works. A window includes its start hour and excludes its end hour, and any hour outside both windows is shoulder. Each period has its own rate, and the fixed fee is added at the end.
  • Tiered uses cumulative caps, for example the first 100 kWh at $0.20, up to 300 kWh at $0.30 and the rest at $0.40. The last cap can be infinite. Each block is charged at its own rate, and a tier of zero width is skipped. A household that used 350 kWh with a $10 fixed fee would pay 100 × 0.20 + 200 × 0.30 + 50 × 0.40 + 10 = $110.

Tests

I wrote the tests with pytest, following the test design in the report: a risk-based focus on reading the file, the tariff edges and the rate windows, with equivalence classes and boundary values to keep the number of tests down.

The 24 tests cover blank and malformed rows, missing headers and a file with no valid rows; the overnight window, a window that does not wrap and the edge hours; repeated tier caps, an infinite final cap and an empty tier list; and zero usage under all three models.

These results are for the command-line build. The report’s coverage run measured main.py, the file that holds the function that reads the usage file and the three tariff functions. The interactive prompt at the bottom of the file is excluded from the measurement, so the figures cover the reading and pricing code and not the prompts.

Interfaces

The command-line interface asks for the path to the usage file and the tariff, then prints the total. In the version the report describes, the time-of-use windows and tier caps are example values built into the prompt block. The pricing functions themselves take any values.

The Flask web interface does the same job in a browser. You upload a CSV or TSV file, choose a tariff, enter its rates and the fixed fee, and get a results page with the cost broken down by period or by tier, the total, and a chart of usage over time. I designed the pages and wrote the Flask code that handles the upload, reads the form and calls the pricing functions. Rows that cannot be read are dropped, and the page warns how many.

Limits

Looking back at the tests, there are gaps worth writing down.

  • The edge-hour test uses the same rate for all three periods, so it shows those hours price without error but not which period each one lands in. The overnight-window test uses different rates and does check the classification, at hours 0, 7, 17 and 22. If the peak window wrongly included its end hour, all 24 tests would still pass, because no test checks hour 21 with different rates. One more assertion would close that.
  • Full statement and branch coverage shows every line and decision ran, not that every result is right.
  • The figures describe the command-line build only. The prompt block and the web interface are not part of them.
  • Each run prices one tariff. Comparing the three means running the tool three times.
